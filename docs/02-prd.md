## 1. 产品定义

AI Museum 是一个面向 9–12 岁访客的开源历史人物学习平台，也是一个面向维护者的声明式人物包运行框架。平台统一提供基于真实 LLM API 的可信对话、长期线程、分层记忆、知识图谱、关系网络、历史时间线、语音交互、知识加工 Agent、评测 Agent 和受控媒体 Provider。

公开 MVP 首发包含至少 3 个按历史时期划分的人物组，每组 12 个达到发布门槛的唯一人物，共至少 36 个可对话人物。首发矩阵、层级建议和内容门槛以 `02-character-roster-v2.md` 为准。人物内容不写死在平台中，任何贡献者都应能通过标准模板创建或维护人物。

MVP 的正式运行路径必须接入至少一个生产级 Model Provider 和一个 Embedding Provider。模型提供自然语言理解和生成能力，RAG/Claim 层提供可回答事实边界；任何模型都不能绕过正式 Claim、人物认知边界、记忆来源和人工知识审核。

## 2. 产品目标与非目标

### 2.1 P0 目标

1. 让儿童与可信历史人物进行连续、适龄、有来源的文字对话。
2. 人物切换、刷新和服务重启后恢复各自长期线程。
3. 实现人物隔离的关系记忆和可追溯的 compact 对话上下文。
4. 展示人物关系网络和与当前问题相关的历史时间线。
5. 建立声明式人物包模板、校验器、样例和贡献文档。
6. 支持史料上传、网络公开来源登记、Candidate Claim 生成和人工审核。
7. 接入真实 LLM API，实现流式人物回答、结构化输出、Episode Summary、候选记忆和适龄改写。
8. 接入真实 Embedding API，实现 Claim、证据、摘要和人物记忆的语义检索。
9. 建立模型调用的 Prompt 版本、Trace、token、费用、延迟、重试和质量评测记录。
10. 保留清晰的 Mock 模式用于自动化测试与无 Key 的开源开发环境，但正式 MVP 不以 Mock 交付。
11. 完成 3 个历史时期人物组、每组 12 人的发布内容，形成可用于展厅、关系搜索、卡册和主题卡包的 36 人首发网络。
12. 同时达到“好用、好玩、有教育意义”三类发布门槛：历史展厅优先、儿童可独立完成核心流程、抽取与人物状态不会因关闭或重试丢失。

### 2.2 P1 目标

1. Push-to-talk 语音输入与适龄语音输出。
2. Museum Guide 跨人物学习路线。
3. 网页创作台完整创建、导入、审核、试聊与导出体验。
4. 可信网络来源发现 Agent，生成待审核补充建议。
5. 经许可的人物与访问者合影。

### 2.3 P2 目标

1. 机构课程、班级或博物馆导览模式。
2. 插画、分镜、语音导览和视频生成。
3. 匿名公共改进数据飞轮，但必须显式加入。
4. 人物包社区目录、维护者协作和更高级发布治理。

### 2.4 非目标

- 人物自主联网、自由调用工具或与其他人物私下自主交流。
- AI 自动发布正式历史知识。
- 为每个人物训练独立大模型。
- MVP 声音克隆、开放代码插件和完整社交网络。
- 以留存、时长或对话数量作为首要成功指标。
- 付费购买探索积分、付费抽卡、限时概率提升或以损失厌恶驱动儿童回访。

## 3. Personas

### Persona A：好奇的 9–12 岁访客

- 想直接问“爱因斯坦小时候数学好吗？”或“你和玻尔为什么争论？”
- 希望得到短而清楚的回答，并能继续追问。
- 可能更愿意说话而不是长时间打字。
- 不理解 Claim、Embedding 等技术术语，需要自然呈现来源和不确定性。

### Persona B：家长或教师

- 关心内容是否适龄、准确、安全。
- 希望看到主题掌握度和推荐路线，但不应默认读取孩子全部私聊。
- 需要关闭记忆、语音或外部模型的控制选项。

### Persona C：人物维护者

- 使用 Git 模板或创作台建立新人物。
- 上传史料、登记网页、处理重复和冲突 Claim。
- 希望所有关系、时间线和引用可版本化、导入导出。

### Persona D：审核者

- 检查身份、史料、争议、许可、适龄性和评测报告。
- 需要明确看到 AI 提取与正式知识之间的门禁。

## 4. 核心场景、痛点与理想方案

| ID | 优先级 | 场景 | 当前痛点 | 理想方案 |
|---|---|---|---|---|
| S1 | P0 | 首次与人物对话 | 普通聊天会幻觉，来源不清 | 使用已发布 Claim，答案展示易懂引用与人物包版本 |
| S2 | P0 | 切换人物后返回 | 历史丢失，人物没有连续关系 | 每个用户与每个人物一条长期线程，本地即时恢复后服务端同步 |
| S3 | P0 | 人物自然回忆 | 错记会令人不适，记忆不可解释 | 仅召回相关且有来源的记忆，显示回调来源，可否认、暂停、删除 |
| S4 | P0 | 长对话超出 Context | 截断后人物忘记前情 | 原文永久归档，分段 compact 为派生摘要，按相关性组装上下文 |
| S5 | P0 | 探索关系与时间 | 单轮问答难以形成历史结构 | 从 Claim 构建权限过滤的关系网络与时间线，并支持跳转相关人物 |
| S6 | P0 | 创建新人物 | 新人物通常需要修改代码 | 提供标准人物包模板、Schema、CLI 校验和私有预览 |
| S7 | P0 | 上传或登记史料 | AI 提取可能错误或无许可 | 统一素材流水线，Candidate Claim 必须绑定来源位置并人工审核 |
| S8 | P0 | 网络补充公开资料 | 搜索结果可信度和版权不稳定 | 可信域策略、SSRF 防护、来源快照元数据、摘录许可和人工确认 |
| S9 | P1 | 语音提问 | 儿童输入长问题不便 | Push-to-talk、可编辑转录稿、适龄 TTS，明确音频保存策略 |
| S10 | P1 | 跨人物学习 | 用户不知道下一步找谁 | Guide 只读取掌握度与线程主题摘要，解释推荐原因并允许跳过 |
| S11 | P1 | 生成合影 | 肖像、人物形象和素材许可混乱 | 用户单次授权、人物包 likeness 权限和 Provider 三重门禁 |
| S12 | P0 | API 限流、超时或不可用 | 静默规则降级会产生能力错觉，重复请求可能重复扣费 | 保留任务状态和部分输出，明确错误、重试时间与恢复动作；不伪造模型结果 |
| S13 | P0 | 开源贡献者没有 API Key | 无法运行真实模型，但测试仍需可重复 | Mock 只用于开发和 CI，并在 UI、响应和文档中显著标记 |
| S14 | P0 | 模型输出格式或引用错误 | 自然语言输出难以稳定进入业务流程 | 使用结构化 Schema、引用核验和有限自动修复，失败时拒绝发布结果 |
| S15 | P0 | 首发人物过少，卡包和关系探索很快耗尽 | 少量样例无法形成持续发现，也无法验证跨时期内容协议 | 按历史时期发布3组×12人；每组形成至少3个展厅和可追溯关系网 |
| S16 | P0 | 人物只有卡面，没有足够可信内容 | 抽到角色后无法进行有深度、有来源的对话 | 人物达到来源、Claim、关系、边界、评测和许可门槛后才进入公开卡池 |
| S17 | P0 | 儿童看不清文字或难以点击 | 小字号、低对比和小控件让界面看似精致但无法使用 | 儿童正文18px、48px触控区、4.5:1对比度和单一主动作成为发布硬标准 |
| S18 | P0 | 抽到人物后状态不一致或结果丢失 | 关闭动画、刷新或断线可能造成扣分但人物未入册 | 服务端先原子持久化抽取结果，再播放可跳过动画；全站按characterId读取拥有状态 |
| S19 | P0 | 抽卡压过历史探索 | 用户进入时期馆后首先被引导消费积分 | 推荐展厅是时期馆主动作；首次开包必须发生在一次真实历史相遇之后 |
| S20 | P0 | 未获得人物变成不可理解的剪影 | 卡牌机制阻断公共历史知识 | 姓名、生平、来源和展厅始终开放，只将长期线程与关系记忆作为解锁能力 |
| S21 | P1 | 新用户在第一次惊喜前等待过久 | 需要多次任务才能抽卡，无法理解完整循环 | 首次有效人物相遇后提供一次免费且保证未拥有角色的开包体验 |

## 5. 主要用户流

### 5.1 访客首次学习

1. 访客进入人物馆，先看到3个首发历史时期组及各自推荐展厅，不一次性铺开36张人物卡。
2. 选择人物后获得一条匿名长期线程。
3. 输入或说出问题。
4. Runtime 执行适龄策略、边界判断、Embedding 检索、Claim/证据检索和记忆召回。
5. Model Provider 根据受控上下文流式生成回答；Runtime 在输出过程中和完成后执行引用、Claim 与越界核验。
6. 回答以儿童可理解的语言展示；来源默认简洁，可展开查看。
7. 相关实体进入关系网络，相关事件进入时间线。
8. 系统异步调用模型产生 Episode Summary、低敏记忆和学习证据候选。

### 5.2 切换人物并保持隔离

1. 用户从爱因斯坦切换到玻尔。
2. 前端先恢复玻尔本地缓存，再分页同步服务端线程。
3. 玻尔只能读取玻尔线程与玻尔关系记忆。
4. 玻尔可以读取“量子理论：practicing”之类的全局掌握度，但不能知道其来源是爱因斯坦私聊。
5. 返回爱因斯坦时恢复原线程和对应人物包 epoch。

### 5.3 长对话 compact

1. 原始消息追加保存，不因 compact 被覆盖。
2. 当活跃上下文达到阈值，后台创建一个 Episode Summary。
3. Summary 保存源消息起止 ID、生成模型、人物包版本、时间和摘要版本。
4. 上下文组装使用：近期原文 + 活跃摘要 + 相关长期记忆 + 正式 Claim。
5. 用户搜索历史或查看记忆来源时读取原始消息，而不是只读摘要。
6. 摘要错误可以重新生成；旧摘要保留审计版本或标记 superseded。

### 5.4 人物包创建与维护

1. 维护者复制标准人物模板或在创作台创建草稿。
2. 填写身份、年代、语言、教育目标、边界、作者与许可。
3. 上传文件或登记公开网络来源。
4. Curator 编排哈希去重、OCR/转录、分段、实体消歧和 Candidate Claim 提取。
5. 审核界面按新增、重复、冲突、低置信、证据缺失分类。
6. 维护者逐项接受、修改或拒绝。
7. 正式 Claim 生成关系边和时间事件，并进入私有预览索引。
8. 校验通过后导出 ZIP、提交发布或通过 Git 发起贡献。

### 5.5 网络可信来源补充

1. Curator 或维护者提出缺口，例如“缺少玻尔与爱因斯坦初次会面的来源”。
2. Source Discovery 只访问允许的公网 HTTP(S) 地址，并执行 DNS/IP/重定向 SSRF 检查。
3. 系统记录标题、作者、发布日期、访问日期、URL、内容哈希、许可和允许保存的摘录。
4. 来源按机构档案、大学、博物馆、论文、出版社、百科等类型标记，而不是给出不可解释的单一“可信分”。
5. 新内容只生成 Candidate Claim；人工审核后才进入新人物包版本。
6. 网页变化、删除或许可撤销后重新计算 Claim 支持状态。

### 5.6 用户控制记忆

1. 用户或监护人在记忆中心查看人物记忆、显式画像和学习状态。
2. 每条记忆展示内容、人物范围、来源、置信度和最近使用时间。
3. 用户可以纠正、暂停、忘记或关闭自动记忆。
4. 用户否认主动回忆后，该记忆立即停止主动使用并进入待确认或低置信状态。
5. 删除账户时按托管服务政策删除个人历史、派生摘要、Embedding 和个人产物。

### 5.7 按历史时期扩展人物与卡池

1. 维护团队按照 `02-character-roster-v2.md` 分别建立盛唐与东亚交流、欧洲文艺复兴与早期科学革命、现代物理革命三组内容骨架。
2. 每组先用锚点人物和关系人物建立 Claim、事件、地点与组织网络，再补充到12人；不能先画卡面再用无来源模型知识填充角色。
3. 单个人物达到来源、Claim、关系、边界、评测和许可门槛后，才能标记为 `publish-ready`。
4. 每组12人全部发布且至少3个历史展厅可用后，才开放该组公开卡池。
5. 用户可以浏览全部人物的基本生平与展厅；获得人物卡后解锁长期对话、关系记忆和收藏状态。
6. 同一人物只对应一个人物包身份和一条用户长期线程，即使未来进入多个主题组也不能生成副本。

### 5.8 首次十分钟体验

1. 用户选择儿童或成人模式后，只看到3个历史时期和一个明确推荐入口。
2. 用户选择时期并进入推荐展厅；卡包不是此时的主动作。
3. 用户与推荐人物完成一次引导式博物馆相遇，并查看至少一条可理解的史料依据。
4. 系统记录有效学习证据，给予探索星并开放一次不消耗积分、保证未拥有人物的首次开包。
5. 服务端在返回结果前完成抽取结果、人物拥有状态、保底和账本的原子写入。
6. 动画结束、跳过、关闭、刷新或断线恢复后，用户都能进入同一个新人物结果。
7. 用户选择“开始长期对话”或“先看相关历史”，两者必须分别进入真实线程或真实展厅。

## 6. 功能需求

### 6.1 身份、线程与消息

- FR-001：匿名访客使用 HttpOnly、Secure、SameSite Cookie 标识。
- FR-002：每个 `userId + characterId` 默认对应一条持续线程。
- FR-003：登录合并必须幂等，不重复消息、epoch、记忆或任务。
- FR-004：消息永久归档直到用户主动删除或托管合规策略要求清除。
- FR-005：消息记录人物包版本、epoch、Claim、引用和生成模式。
- FR-006：前端切换人物时先恢复本地缓存，再服务端分页同步。

### 6.2 分层 Memory

- FR-010：区分原始消息、Episode Summary、显式画像、人物关系记忆、偏好、Open Loop 和学习证据。
- FR-011：compact 是可追溯派生物，不得覆盖原始消息。
- FR-012：每条 Summary 和 Memory 必须保存源消息范围或显式输入来源。
- FR-013：人物关系记忆只能由对应人物读取。
- FR-014：敏感或可识别个人信息默认不自动形成长期记忆。
- FR-015：用户否认后停止主动召回；纠正后生成新版本并保留变更记录。
- FR-016：上下文组装必须有 token 预算，并按系统规则、人物边界、Claim、近期消息、摘要和记忆的优先级裁剪。
- FR-017：用户可导出和删除原始消息、摘要、Embedding 与个人 Memory。

### 6.3 知识图谱、关系与时间线

- FR-020：正式知识以 Claim 表达，保存主体、关系、客体、时间、状态、来源和可信等级。
- FR-021：同一问题的矛盾 Claim 可以并存，并标记争议。
- FR-022：Entity、Relationship 和 Timeline Event 都必须可回溯到 Claim。
- FR-023：已发布人物包版本不可覆盖；每次修改生成新版本。
- FR-024：历史版本、已撤销来源和失效 Claim 永久保留审计元数据，但不得继续进入公开回答索引。
- FR-025：人物关系网络按权限、人物包版本和认知边界过滤。
- FR-026：时间线区分人物亲历、当时可知、身后事件和博物馆旁白。

### 6.4 人物包与开源扩展

- FR-030：官方提供人物包 Schema、最小模板、完整样例、CLI 校验器和贡献指南。
- FR-031：第三方人物包不允许包含脚本、二进制插件或任意可执行代码。
- FR-032：导入导出保持 ID、来源、关系、版本和许可一致。
- FR-033：Fork 保留原作者、来源包和派生关系，不能冒充原作者。
- FR-034：平台代码默认 Apache-2.0；人物包和媒体分别声明许可。
- FR-035：样例人物必须和社区人物使用相同运行接口，不得存在爱因斯坦专用逻辑。

### 6.5 素材与可信网络来源

- FR-040：支持 PDF、Markdown、文本、图片、音频、视频、字幕和 URL。
- FR-041：上传执行文件类型、大小、恶意内容、哈希去重和许可检查。
- FR-042：URL 执行 SSRF、重定向、私网 IP、超时和下载大小限制。
- FR-043：无明确许可时只保存 URL、元数据、允许摘录和处理结果。
- FR-044：AI 提取只能创建 Candidate Claim，不能自动发布。
- FR-045：删除来源或撤销许可后重新计算 Claim 支持与检索索引。

### 6.6 Character Chat Runtime

- FR-050：执行年龄适配、问题分类、人物边界、图谱检索、证据检索、记忆召回、生成、引用核验和越界复检。
- FR-051：公开回答只使用当前线程固定人物版本中的正式 Claim。
- FR-052：人物第一人称与博物馆旁白明确分离。
- FR-053：低置信记忆使用不确定表达，不得使用确定性“你还记得”。
- FR-054：规则、云模型和本地模型必须在 UI 中明确区分。
- FR-055：历史消息、来源文本和 Memory 都作为不可信输入，不能覆盖系统规则。
- FR-056：正式人物回答必须通过服务端 Model Provider 流式返回，支持用户取消生成。
- FR-057：问题分类、引用计划、记忆候选和边界结果优先使用 Schema 校验的结构化输出。
- FR-058：若回答中的历史断言无法映射到当前人物版本的正式 Claim，必须删除、重写或拒绝该断言。
- FR-059：记忆提取、Episode Summary 和掌握度分析异步执行，不得阻塞聊天首 token。

### 6.7 语音与媒体

- FR-060：语音输入采用 push-to-talk，提交前允许查看或编辑转录文本。
- FR-061：默认不永久保存儿童原始音频；若保存必须单独说明用途并取得适当同意。
- FR-062：TTS 只能使用受许可声音，不默认克隆历史人物声音。
- FR-063：媒体生成依次检查用户授权、人物媒体许可和 Provider 可用性。
- FR-064：媒体产物保存参数、来源、人物版本和授权记录。

### 6.8 Agent Task

- FR-070：任务支持 queued、planning、running、waiting_review、completed、failed、cancelled。
- FR-071：任务步骤、工具、耗时、模型、费用、重试和失败原因可审计。
- FR-072：Agent 只能调用 Zod 校验的白名单工具。
- FR-073：发布、敏感授权、高成本生成和用户照片上传必须等待人工确认。
- FR-074：Knowledge Curator 和 Source Discovery 不能直接修改正式人物版本。

### 6.9 Model、Embedding 与 API Runtime

- FR-080：正式 MVP 至少配置一个生产级 Model Provider 和一个 Embedding Provider。
- FR-081：平台业务接口不得直接依赖供应商 SDK；供应商差异封装在 Provider 适配层。
- FR-082：API Key 仅存在于服务端 Secret 配置，不进入浏览器、人物包、任务输入、Prompt、日志或导出产物。
- FR-083：每次调用记录内部 Trace ID、Provider、模型、Prompt 版本、输入输出 token、延迟、重试、错误码和估算费用；不得记录未脱敏敏感内容。
- FR-084：聊天调用支持超时、取消、有限重试和断流错误；非幂等生成不得无条件重复提交。
- FR-085：结构化模型输出必须经过 Zod/JSON Schema 验证，最多有限自动修复，仍失败则进入可解释失败状态。
- FR-086：Model Provider 不得自行联网；需要公开网络资料时必须通过 Source Discovery 的白名单工具与审核流水线。
- FR-087：每个调用必须有明确 token 与费用预算；超预算时优先压缩旧上下文、降低非必要候选数量或等待确认，不得丢弃当前 Claim 证据。
- FR-088：Prompt 模板、模型配置和评测集必须版本化，使历史回答可以定位到当时的运行配置。
- FR-089：Mock Provider 只用于 CI、演示和无 Key 开发环境，其输出必须带 `mock` 标识且不能被当作正式评测结果。

### 6.10 首发人物矩阵与卡池内容

- FR-090：公开 MVP 至少发布3个按历史时期划分的人物组，每组恰好12个可抽取人物，首发至少36个唯一人物。
- FR-091：首发名单、主要角色、建议层级和关系入口以 `02-character-roster-v2.md` 为内容基线；替换名单必须在 Stage 2 重新审批并记录原因。
- FR-092：每个公开人物必须满足至少3个独立可靠来源、20条已审核 Claim、5条正式关系和12道发布评测的门槛。
- FR-093：每组必须包含至少3个完整历史展厅，每个人物至少属于1个展厅，组内关系图必须连通或形成不超过2个可解释子网络。
- FR-094：未达到发布门槛的人物不得以占位卡、仅卡面或无来源对话角色进入公开卡池。
- FR-095：每组卡池使用版本化人物清单；单个人物包升级不改变用户已获得状态，也不得创建重复人物线程。
- FR-096：五档层级只表示组内策展中心度、内容深度与关系覆盖，不得在文案中解释为道德价值、智力或全历史统一排名。
- FR-097：每组默认层级分布为白3、蓝3、紫3、橙2、金1；任何调整必须在卡池发布前版本化并说明策展依据。
- FR-098：卡池只有在12个人物全部达到公开发布状态后开放；维护端可以预览未完成组，但访客端不得抽到草稿人物。
- FR-099：人物基础生平、来源和展厅不因未获得卡牌而隐藏；卡牌解锁的是长期对话、关系记忆和收藏体验。

### 6.11 体验完整性与无障碍

- FR-110：历史时期馆的唯一主动作是进入推荐展厅；卡包作为次级入口，不得先于历史内容出现。
- FR-111：儿童模式正文至少18px、辅助文字至少14px、行高至少1.6，主要交互触控区至少48×48px且间距至少8px。
- FR-112：正常文字对比度至少4.5:1、大字至少3:1；颜色不能作为层级、状态或错误的唯一编码。
- FR-113：所有可点击卡片使用按钮或链接语义，支持键盘、可见焦点和适当的模态框焦点管理。
- FR-114：人物拥有状态以稳定 `characterId` 集合保存；搜索、卡册、时期馆、人物页、线程和登录合并必须读取同一事实。
- FR-115：抽取结果、扣分、保底、重复补偿和拥有状态在同一服务端幂等事务中提交；揭晓动画不承担写入职责。
- FR-116：关闭、跳过、刷新、断线和客户端重试必须恢复同一抽取结果，不得再次扣分或重新随机。
- FR-117：首次有效历史相遇后提供一次免费且保证未拥有角色的开包；免费资格按用户幂等消费。
- FR-118：未获得人物的姓名、肖像、年代、基本生平、来源和展厅保持开放，并允许一次引导式博物馆相遇。
- FR-119：按钮文案必须与实际目的地一致；“开始长期对话”只能进入对应人物的唯一长期线程。
- FR-120：所有奖励动画支持跳过和 `prefers-reduced-motion`，关闭动画不能丢失结果。
- FR-121：儿童与成人模式功能、人物数据和抽取规则完全相同；只允许视觉密度、字号和辅助信息呈现不同。
- FR-122：Toast 只用于非关键瞬时反馈；错误恢复、扣分结果、授权和必须阅读的信息使用持久界面。
- FR-123：正式人物入口使用肖像加姓名；单字或首字母只允许作为开发占位，不能成为公开版主要识别方式。

## 7. 记忆生命周期设计要求

### 7.1 平台知识图谱

- 目标是永久、版本化、可审计留存。
- “永久”指历史记录不因新版本覆盖而消失。
- 来源撤销后保留 ID、哈希、变更和审计元数据；受限制原文按许可要求删除或封存。
- 失去证据的 Claim 退出可回答索引，但历史版本仍能解释旧对话为何产生。

### 7.2 用户聊天与 Profile

- 原始消息尽量长期保存，直到用户或监护人删除。
- Compact 不等于删除：它产生 Episode Summary、主题索引和 Embedding，用于有限 Context。
- Profile 分为用户显式填写和系统推断；9–12 岁用户的系统推断默认人物隔离、低敏、可见且可撤销。
- 托管服务不能承诺法律意义上的绝对永久，必须提供数据导出、删除、备份清除周期和账户恢复策略。

### 7.3 Context 组装

建议每轮采用：

1. 系统与安全规则；
2. 当前人物包、边界和版本；
3. 当前问题命中的正式 Claim 与证据；
4. 最近原始消息；
5. 相关 Episode Summary；
6. 相关人物关系记忆和 Open Loop；
7. 不含来源的全局掌握度信号。

达到 token 阈值时优先压缩较旧对话，不压缩系统规则、当前证据和最近消息。

正式模型调用采用两类路径：

- **同步低延迟路径**：问题分类、检索规划、人物回答与流式输出。只允许读取，不允许修改人物包或执行外部工具。
- **异步智能路径**：Episode Summary、记忆候选、掌握度证据、知识候选提取和评测。通过 Agent Task/Worker 执行，可重试、暂停和审计。

## 8. Success Measurement

### 8.1 记忆否认率

定义：人物主动提起某条长期记忆后，用户明确表示“不对、没说过、记错了”或通过记忆中心纠正/删除的次数，占全部可评价主动回忆次数的比例。

公式：

`Memory Denial Rate = 被否认的主动回忆 / 有反馈机会的主动回忆`

它是可信度护栏，不是商业指标。它用于发现错误抽取、错误归属、过度确定措辞和不相关召回。沉默不能自动当作认可；早期应结合显式“记得/不对”反馈和人工抽样。MVP 建议在至少 200 次可评价回忆后，以低于 5% 为目标，并单独追踪跨人物泄露，后者必须为 0。

### 8.2 第三方人物创建时长

原先的“60 分钟”不是要求一小时完成一个史料充分、可公开发布的人物，而是衡量平台扩展门槛：一个具备基本开发能力的贡献者，使用准备好的少量合法来源，从复制模板到获得第一个可对话的私有预览需要多久。

定义两个指标：

- `Time to First Private Preview`：复制模板到 Schema 校验通过，并能用至少 1 个来源、3 个审核 Claim 完成私有试聊。MVP 中位数目标不超过 60 分钟。
- `Time to Publish-ready Character`：达到来源、边界、许可、评测和审核标准的时间。该指标受人物复杂度影响，不设置一小时目标，只记录流程中最耗时的步骤。

### 8.3 MVP 质量指标

| 指标 | 目标 |

### 8.4 学习体验评测

- 9–12 岁语言是否清楚、不过度幼稚且不篡改事实。
- 用户追问时是否延续上下文而不是重复首答。
- 人物不知道的内容是否正确转交博物馆旁白。
- 关系图和时间线是否帮助回答当前问题，而不是制造视觉噪音。
- 语音转录错误是否能在提交前被发现和纠正。

## 9. 安全、隐私与治理

- 托管版本需在正式上线前确定儿童账户、监护人同意和地区合规方案。
- 默认不收集真实姓名、学校、精确地址、联系方式和生物识别信息。
- 儿童敏感 Memory 自动启用必须关闭。
- 原始音频默认短期处理后删除；转录稿按消息策略保存。
- 所有个人数据支持导出、遗忘和账户删除。
- 网络材料、文档内提示词和历史消息均视为不可信输入。
- 人物包发布必须通过身份、已故状态、史料、争议、许可、适龄性和评测审核。

## 10. 依赖与风险

- 需要确定托管服务的儿童隐私与监护人模型。
- 需要为可信公开网络来源建立策略，而不是把“公开可访问”等同于“可复制、可信或可训练”。
- PostgreSQL Repository、对象存储和队列尚未替代本地演示 Store。
- 真实 LLM、Embedding、转录、TTS 和图像 Provider 尚未选型。
- MVP 需要选择一个主 Model/Embedding Provider，并为超时、限流、配额与数据处理条款准备降级策略。
- 模型成本尚无真实使用基线；在本地评测和小范围试用后确定单次有效学习会话预算。
- 关系图和时间线质量依赖 Claim 的时间建模与实体消歧。
- 36个完整人物包会显著扩大史料、许可、评测和中文适龄改写工作量；允许分批生产和内部验证，但不能降低公开卡池的单人物门槛。
- 五档层级容易被误解为人物价值排名；产品文案、卡面和维护指南必须持续说明它只表示当前历史组中的策展深度。
- 三个时期跨越中文史、欧洲艺术史与现代科学史，需要不同领域审核者；单一维护者不能独立批准全部36人。
- 如果 P0 同时包含完整语音、网页创作台和网络发现，可能超出单次 MVP，需要在技术架构阶段拆分发布切片。

## 11. PRD 验收边界

PRD 获批后，Stage 3 必须产出可视化设计，而不是只写文字。至少覆盖：

- 9–12 岁人物馆与首次对话；
- 文字/语音输入、引用、旁白和边界回答；
- 人物切换与历史恢复；
- 记忆回调、否认和记忆中心；
- 关系网络与时间线；
- 人物模板/创作台和 Candidate Claim 审核；
- 正常流式生成、用户取消、API 限流、断流、无 Key Mock、无许可和失败恢复状态。
